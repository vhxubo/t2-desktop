# 进程级状态快照事故报告（2026-11-25）

## 定性

- **级别**：P2（功能降级，无数据损坏、无凭据泄露、无服务端写错）
- **类型**：客户端初始化时序缺陷——在 app 构造时快照了晚于构造才就绪的进程级状态
- **结论**：本次问题不是服务端接口、网络、限流、SSE 或系统通知权限故障；Windows 正式启动路径本身支持原生通知，根因是通知函数没有被传到界面状态。回调协议注册失败提示属于同一类快照问题。
- **影响范围**：正式启动的桌面客户端（Windows / macOS / Linux）。无头 UI 测试与渲染截图不受影响，因为它们不经过 `WhenReady` 和 `RegisterURLScheme` 之后的生产时序。

## 根因

### 1. 原生通知函数被构造时快照

生产启动顺序是：

1. `newDesktop` 建进程级单例，此时 `desktop.notify` 为 `nil`；
2. `newMainApp` 构造界面状态，旧代码在这里执行 `a.notify = d.desktop.notify`，快照到 `nil`；
3. `mygo.App.WhenReady` 里先调用 `mygo.NotificationsSupported()`，再把 `showNativeNotice` 写到 `desktop.notify`；
4. 后续没有任何代码把新值同步回 `a.notify`。

于是通知窗口按 `a.notify == nil` 画成「原生通知不可用」并隐藏开关；`showNotices` 也在同一判断处直接返回。SSE、未读数、列表和偏好设置都正常，只是系统弹窗没有真正发出。

### 2. 回调协议注册失败提示同样被快照

`newMainApp` 早于 `mygo.App.RegisterURLScheme`。旧代码在构造时把空的 `desktop.schemeWarn()` 复制进 `a.schemeWarn`；注册失败后 `d.schemeWarn` 虽然被写入，登录页仍读旧快照，用户看不到「浏览器授权后不会自动跳回，请复制回调链接」的提示。

### 3. 测试没有覆盖生产时序

无头 UI 测试用 `newApp`，没有进程级 `desktop`，也不进入 `WhenReady` / `RegisterURLScheme`。因此：

- `a.notify` 本来就是 `nil`，`notifications_test.go` 还把「原生通知不可用」当作预期文案；
- 登录页测试直接给 `a.schemeWarn` 注入字符串，绕过了真实注册流程。

测试验证的是无头渲染路径，没有验证「构造后才装上的进程级状态对界面可见」，所以两个生产缺陷都没有被拦住。

## 影响

- **原生通知**：正式客户端即使平台支持、用户开关为开，也不会弹出系统通知；通知窗口误报不可用且没有开关。消息中心、未读角标、提醒关键词、免打扰与轮询/SSE 逻辑不受影响。
- **授权回跳**：系统未注册回调协议时，登录页缺少失败说明。用户仍可按代码里的兜底方案手动粘贴浏览器地址栏链接完成授权，但不知道该这么做。
- **安全与数据**：不涉及令牌、账号会话、服务端写入或本地数据损坏。
- **平台权限**：macOS 首次弹窗授权、Linux D-Bus session bus、Windows 专注助手等仍可能影响系统通知展示，但这是修复之外的平台因素，不是本次缺陷。

## 修复

- `notify.go`：新增 `app.nativeNotifier()`，实时读取 `desktop.notify`；`showNotices` 在 UI 线程取一次函数值后交给通知协程使用。
- `notifications_ui.go`：通知可用性判断改用 `nativeNotifier()`。
- `main.go`：删除 `app.notify` 快照字段；新增 `app.schemeWarning()`，有 `desktop` 时实时读取注册结果，无头测试仍可给 `app.schemeWarn` 注入。
- `main.go`：登录页改用 `schemeWarning()`；`newAppWithDeps` 的注释集中说明哪些进程级状态不能快照。
- `desktop.go` / `main.go`：清理未使用的 `desktop.afterReady` 与 `app.tray`，避免留下会被误当成真实来源的槽位。
- 回归测试：
  - `TestNativeNotifierInstalledAfterAppConstruction`：先构造 app，再装通知函数，验证界面查询和发送路径都能看到它，并验证点击目标登记。
  - `TestSchemeWarningReadAfterRegistration`：先构造 app，再写注册失败信息，验证登录页能显示。
  - 原有无头测试保持不变，继续验证没有 `desktop` 时的回退行为。

## 同类状态审计

| 状态 | 来源 / 晚赋值 | 读取方式 | 结论 |
| --- | --- | --- | --- |
| `notify` | `WhenReady` 中按平台能力赋值 | `nativeNotifier()` 实时读 `desktop` | 已修复 |
| `schemeWarn` | `RegisterURLScheme` 失败后赋值 | `schemeWarning()` 实时读 `desktop` | 已修复 |
| `updates` | `mygo.Use` 之后置位 | `updatesEnabled()`；使用点已全覆盖 | 原本正确 |
| `trayReady` | 托盘创建成功 / 退出时变更 | `trayIsReady()`；关闭行为与设置页已覆盖 | 原本正确 |
| `quitApp` / `openURL` | 建 `desktop` 时即确定 | `quitProgram` 方法值与 `desktop` 字段 | 快照安全 |
| `auth` / `icons` / `updateMgr` | 由 `desktop` 持有，`replaceAuth` 同步客户端 | 实时查询，未复制到 app | 原本正确 |

`a.trayReady` 与 `a.schemeWarn` 的统一兜底只服务无头测试；带 `desktop` 的测试已经改为写 `desktop` 状态，不会误判为生产问题。`nativeNotifier()` 在无 `desktop` 时返回 `nil`，若未来无头测试需要假通知函数，应构造 `desktop` 并注入 `b.notify`。

## 预防

1. 进程级状态只要可能晚于 `newMainApp` 就绪，就不在 `newAppWithDeps` 中快照；统一从 `desktop` 的查询方法读取。
2. 新增这类状态时，补一条「先构造 app、后写入 desktop 状态」的回归测试，用 `testBook` + `newMainApp` 模拟生产时序，不能只测 `newApp` 的渲染。
3. 测试注入字段只作为无 `desktop` 时的兜底，不参与生产判断；代码中已用注释标明。
4. 排查类似问题时，先按启动顺序列出所有晚赋值点，再逐一核对其 UI 与后台读取路径，而不是只看单一症状。
